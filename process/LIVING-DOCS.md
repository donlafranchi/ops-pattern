# Living documents

## Grep-built, never hand-kept — the pattern

**Ruled 2026-09-27 (Don).** He keeps asking for information that spans the project and does not want to maintain any more documents to answer it. **This repo is optimised for agents reading and writing it, not for people maintaining prose — so anything a person needs is generated when they ask, not kept current by hand.** It is lesson 2 and lesson 23 turned from a prohibition into a mechanism.

**Five rules:**

1. **A fact lives inline, at the single place it is true** — the question in the scenario it would change, the claim on the test that makes it, the binding on the ruling that imposes it, the date on the risk that expires. Never a second copy.
2. **A cross-cutting document is generated by scanning for markers, never maintained.** On demand by default (`python3 scripts/markers.py …`). A generated file is committed only when something must read it without running a script — an agent at session start, Don on a phone.
3. **A generated file is never edited directly, and says so in its own header.** `scripts/lint.sh` fails on a generated file whose header does not, and on one that differs from what its sources generate.
4. **Generated documents are rebuilt; authored documents are pruned. Neither accumulates.** When something is superseded — a ruling, a criterion, a section, a whole scenario or note — it is deleted, and the thing that replaced it names it in one line, enough for `git log -S`. Reasoning that still matters moves into the replacement; reasoning that only explained the old position goes with it. **History lives in git and is retrieved on demand, never mirrored in prose.** A file that only ever grows is the failure this rule exists for.
5. **A marker without a lint is decoration** — the failure `process/ABSOLUTES.md` names in `[guard-proves-itself]`. Every marker kind ships with a bad fixture its checker must reject on every run, or the lint fails as inert.

| Marker | Written | Builds | Fails the lint when |
|---|---|---|---|
| `[open-question owner=… raised=…]` | where the question's answer lands — `process/PIPELINE.md` § Open questions | `STATUS.md` § Open questions | owner, date or question missing; sitting in `DECISIONS.md` |
| `[guards F093.4]` | on the line above the check that discharges the criterion — test, script, CI step | `markers.py coverage` (full map, on demand); `STATUS.md` § Guard coverage (summary) | grammar wrong; the scenario or criterion does not exist |
| `[binds tiers=… surfaces=…]` | at the end of a `DECISIONS.md` line — the one edit a past line may take | `constraints/planning.md`, `constraints/code.md` | a decision from 2026-09-21 on has none; a constraints file differs from what `DECISIONS.md` generates |
| `[replaces 2026-09-22: exact old text]`, `[replaces F059: old text]`, `[replaces path.md]` | on the `DECISIONS.md` line that supersedes something — `[newer-decision-wins]` | nothing; it is the one line that lets git find what was deleted | a decision says it reverses or replaces something and names nothing; the named text or file is still present |
| `[evidence YYYY-MM-DD from=<source>: what was seen]` | on a `DECISIONS.md` line that a user's action or words changed | **nothing yet — deliberately deferred**, see below | the shape is wrong — never its absence |
| `"owner"`, `"review_by"` | in each `accepted-risks/*.json` | `STATUS.md` § Deferred on purpose | owner missing; **the date has passed** |

**The evidence marker is for evidence-driven changes only.** Before launch every ruling is Don's judgement, and *why he changed his mind* is his and git's — **a judgement call carries no evidence tag, and none is ever asked for.** That is the normal case and must stay free of ceremony: **the failure mode is every decision sprouting an empty evidence field**, so the lint checks the tag's shape when present and never requires it. After launch, when a ruling changes because of something a member did or said, the tag names what was seen, where it came from and when — so *what has feedback actually changed* is answered by a scan, not reconstructed from git.

**Its generated view is deferred on purpose.** There is no member feedback before 2026-10-30, so a view would scan nothing. **The trigger is mechanical, not remembered:** `scripts/lint.sh` fails the day the first `[evidence …]` tag lands in `DECISIONS.md`, telling whoever added it to build the view (`EVIDENCE_VIEW_BUILT` in `scripts/markers.py`).

**The tiers are the two with a `CLAUDE.md`** — `planning` (this repo, Cowork) and `code` (`socialus-web`, Code). **Each `CLAUDE.md` points at its own constraints file and at no other.** The firewall stays where it already works — which files an agent is told to read — rather than moving into a retrieval system. `planning` still owns and reads `DECISIONS.md`; `code` reads only `constraints/code.md`.

**Where the lint runs.** `scripts/lint.sh` here, locally and in `.github/workflows/lint.yml`. `socialus-web` runs `scripts/check-markers.sh` in its own CI for markers in its code. That repo is public and this one is private, so it cannot check a `[guards …]` claim against a scenario; this repo's lint does, whenever a `socialus-web` checkout is at hand, and `STATUS.md` lists any claim pointing at nothing.

**Deliberately not in scope — refuse these by name, so momentum does not add them:**

- **A marker that restates what a filename or directory already encodes.** `scenario-F093.md` already says it is F093; `accepted-risks/` already says what its files are. A marker that repeats the path has nothing to check, so its lint would check nothing, and rule 4 makes it decoration on arrival.
- **A generated document nobody has a reason to read.** Generating is cheap, and that is the danger: a file built because it could be becomes a thing to regenerate, diff and explain. **Before adding a marker kind, name who asks the question it answers and what lint fails without it.** No asker, no marker.

**Considered, not built:**

- **Deviation markers in code** instead of a `DEVIATIONS.md` (none exists here). **Not built, on purpose:** the rule is that a PR whose behaviour differs from its scenario *stops and asks* (`socialus-web` `CLAUDE.md`). A marker would give a divergence a legitimate place to live in shipped code — the opposite of the rule. Deviations stay in PR descriptions, where they block rather than accumulate.
- **`building` tied to code.** **Built as a report, not a lint** — `STATUS.md` § Is `building` backed by code? counts commits, files and branches naming each `building` scenario. Not a lint, because what to do about a scenario claiming `building` with nothing behind it is a status decision, not a syntax error. On 2026-09-27 it found F069 with nothing, and F060 and F061 named in files but by no commit.

**Adding a marker kind:** a row above, the grammar and checks in `scripts/markers.py`, a bad fixture and a good one in `scripts/fixtures/markers/` with the count in `scripts/lint.sh`, and the lint observed failing before anything relies on it.

## Hooks — what actually fires

**Be honest about which get skipped.**

| Hook | Reliable? | Verdict |
|---|---|---|
| **GitHub Action on PR to `socialus-web`** | **Yes.** Runs on every PR regardless of who opens it or what they have installed. | **Use this.** It is the only one that cannot be skipped. |
| **GitHub Action on push to `main`** | **Yes**, same reasoning. Both repos have remotes. | Use for regenerating facts after a merge. |
| **Local `post-merge` hook** | **No.** A squash-merge through the GitHub UI never touches anyone's machine, so it would not have fired for a single merge this week. | Do not build. |
| **Local `pre-commit`** | **Weak.** `core.hooksPath` can be committed, but every clone must opt in and `--no-verify` skips it. | Only as a fast local echo of a check CI already enforces. |
| **Scheduled Action** | Yes. | Allowed when it commits only if the content moved, so a new revision always means something changed. |

**The important design point: the reliable hook is not "regenerate the doc." It is "fail the PR when a document's claim has become false."** That is the pattern this repo has already learned works — the person-noun lint, the migration drift check, `advisor-diff.sh`. A generated document nobody believes is safe; a check that blocks a merge is what actually holds a rule.

**Concretely, two CI checks worth having**, in order of value:

1. **Doc-claim check on PR.** If a PR closes an issue that a living document still lists as *to build*, fail with the line number. Cheap, and it would have caught the F076 drift the day it happened.
2. **String check on PR** — person-nouns, em dashes, "corner", corporate transitions. Already specified in `nouns.md`; unbuilt.
