# T109 — `/you/following` management page — sections, Unfollow/Leave, undo

## Deviation 1 — Built the missing `group.member_leave` / `group.member_join` handlers (ticket said "no new server actions")

**What:** The ticket Notes claim "all three soft-delete writes reuse handlers shipped by T091 / T070 / T102" and "no new server actions." In reality only `member.unfollow` (T091) and `member.saved_search.remove` (T063/T102) existed. **There was no group join/leave handler at all** — `group/` shipped only create/update-draft/activate, with `group.member_joined` fired solely for the founder inside `group.create`. F035 (the Group Join CTA) is still in `now/`, unbuilt. I added `group.member_leave` (soft `left_at` + `group.member_left` event, idempotent, self-only) and `group.member_join` (upsert: fresh insert role='member'; re-join clears `left_at`, preserves role) plus the `joinGroupAction`/`leaveGroupAction` server-action wrappers (`src/app/_actions/group-membership-actions.ts`).

**Why:** T109's Leave affordance and its Undo (re-activate) cannot function without these handlers; the dependency the ticket assumed was unmet. The handlers mirror the established `member.follow`/`member.unfollow` upsert+soft-delete+event pattern exactly, and writes route through the action layer (no RLS write policy on `group_memberships`).

**Disposition:** flag-for-ticket-rewrite — F035 must adopt these handlers for its Join CTA rather than writing its own, and the T109 ticket's "no new server actions" note is wrong (corrected here).

## Deviation 2 — `group.member_join` has no fresh-join invite/visibility gate (safe for F042's Undo-only use)

**What:** `group.member_join` checks the Group exists and isn't dissolved, but does not gate a **fresh** join by Group kind/discoverability (e.g. it would let a Member insert a membership into a `private`/`family` Group with no invitation).

**Why:** Within F042 the handler is only ever reached via Undo, which re-activates a membership row that already existed (the `on conflict … set left_at = null` path) — never a fresh insert into a group the Member wasn't already in. The proper fresh-join gate (invitation / kind rules) belongs to F035's Join surface, which owns that policy.

**Disposition:** flag-for-spec-revision — see SPEC-PATCHES: F035 must add the kind/discoverability/invite gate to `group.member_join` before exposing a generic public Join CTA.

## Deviation 3 — Venue Undo uses a new `member.saved_search.restore` handler emitting `member.saved_search.updated`

**What:** Venue Unfollow soft-removes via `member.saved_search.remove`; its Undo re-activates the **same row** via a new `member.saved_search.restore` handler (clears `removed_at`), which emits `member.saved_search.updated` (payload `action:'restored'`).

**Why:** `member.saved_search.create` only inserts — using it for Undo would duplicate the row, violating the scenario edge case "re-activate, not duplicate." A dedicated `member.saved_search.restored` event kind would require a migration (the `member_events` CHECK in 019 has no such kind), which this surface deliberately avoids; clearing `removed_at` is genuinely an update, so `…updated` is honest. Owner collapse to `NotFoundError` mirrors `…remove`.

**Disposition:** accepted-as-is. (A dedicated `.restored` event kind is a possible future migration if audit consumers need to distinguish restore from edit.)

## Deviation 4 — DB-row behavior verified by static-shape Vitest + Playwright eval, not live-DB Vitest

**What:** Handler tests (`tests/actions-t109.test.ts`) assert file existence, zod validation, registry wiring, and source-shape (soft-delete column, event kind, conflict clause, owner collapse) — not live row writes. Component tests mock the server actions.

**Why:** Matches the established no-live-DB-Vitest convention for handlers (T091/T075/T102). End-to-end row/event assertions are the F042 Playwright eval's job (downstream `test` skill).

**Disposition:** accepted-as-is.

## Deviation 5 — New "Following" card-scroll coexists with the legacy old-schema `/you` "following" tab

**What:** The existing `/you` page still has a vendor-schema "following" tab (`follows.vendor_id`). T108's new-schema "Following" summary section (Members/Groups/Venues) was added alongside it, not replacing it.

**Why:** The rebuild is in flight; the old vendor surfaces haven't been retired. Replacing/removing the legacy tab is out of F042's scope and would risk the live vendor experience. The new section is self-contained and self-omits when empty.

**Disposition:** flag-for-ticket-rewrite — the legacy vendor `/you` tabs (saved/following on `businesses`/`follows`) want a dedicated retirement ticket once the new-schema surfaces are the default.
