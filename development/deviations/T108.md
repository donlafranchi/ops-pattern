# T108 — Unified follows reader + `/you` "Following" summary

## Deviation 1 — `getMemberFollows` is isomorphic (takes a SupabaseClient), not a server-only reader

**What:** The ticket calls for a "server-side reader." It's implemented as a pure function taking a `SupabaseClient`, so the server page (`/you/following`, T109) calls it with the server client and the client `/you` summary calls it with the browser client. Both are RLS-bound to the authenticated Member.

**Why:** The existing `/you` page is a `'use client'` component (old vendor schema). Threading a server-only reader into it would mean a new API route or server action just to fetch. An isomorphic function satisfies "one reader, two surfaces" (review-F042 § Recommendations) without new transport surface, and the RLS guarantee is identical whichever client runs it (owner-only on `member_saved_searches`/`group_memberships`; public-read on `member_follows`). Anchored to `src/lib/supabase.ts` (browser) + `src/lib/supabase-server.ts` (server).

**Disposition:** accepted-as-is.

## Deviation 2 — Group/Venue hrefs use the slug-only short path (`/p/g/[slug]`, `/p/l/[slug]`), not the full place-scoped URL

**What:** Person cards link to the canonical `/m/[handle]`. Group and Venue cards link to `/p/g/[slug]` / `/p/l/[slug]` rather than the fully place-scoped `/p/[…place]/g/[slug]`.

**Why:** The `/p/[...slug]` catch-all (`src/app/p/[...slug]/page.tsx`) resolves Groups and Venues off the **globally-unique slug alone** — `splitGroupSlug` / `splitLocationSlug` accept an empty place prefix, and `resolveShop`/`resolveVenue` key on slug, treating the place path as breadcrumb context only. No forward place-path builder exists in the codebase (the canonical Member page itself renders Group memberships as non-linked chips for the same reason). The short path navigates correctly today; canonical place-path enrichment is deferred until a forward place-path resolver exists.

**Disposition:** flag-for-spec-revision — see SPEC-PATCHES (a shared `groupHref`/`venueHref` helper that resolves the full place path, once forward place-path resolution is built; would also fix the canonical Member page's non-linked Group chips).

## Deviation 3 — No image thumbnail for Group/Venue cards (schema has no image column)

**What:** Only Person cards show a thumbnail (`members.avatar_url`). Group and Venue cards always render the initial-letter placeholder.

**Why:** Neither `groups` nor `locations` carries an image/avatar column at b1 (migrations 014 / 007). The reader returns `thumbnailUrl: null` for those kinds, which the card recipe renders as the kind-appropriate placeholder per the DLS recipe — not a deviation from intent, just a note that "thumbnail" only resolves for People until a Group/Location image column ships.

**Disposition:** accepted-as-is.
