# T104 — Venue page shell (route, header, CTAs, About, auth gating)

## Deviation 1 — Route folds into the `p/[...slug]` catch-all, not a standalone `l/[slug]/page.tsx`

**What:** The ticket AC says "Create `web/src/app/p/[...place]/l/[slug]/page.tsx`." Next.js App Router forbids a static segment (`/l/`) after a catch-all (`[...slug]`) — the exact limit recorded in the T060 DEVIATION and the `p/[...slug]/page.tsx` header comment. The Group, product, service, and gathering pages all fold their dispatch into the single `p/[...slug]/page.tsx` catch-all (split-by-marker). T104 adds a `splitLocationSlug` (`/l/` marker) dispatch alongside them in both `generateMetadata` and `PlacePage`.

**Why:** Structural Next.js constraint, not a design choice. Mirrors the shipped Group dispatch exactly; no new routing infrastructure. The public URL is still `/p/[…place]/l/[slug]` per ADR-20 — only the file layout differs from the ticket's literal path.

**Disposition:** accepted-as-is. No SPEC-PATCHES entry — the catch-all fold is already the documented T060 pattern; the DLS § Venue page was updated with a URL note.

## Deviation 2 — Distance needs a new read-only RPC (`032_venue_distance.sql`); ticket asserted "no new migrations needed"

**What:** The ticket's Notes say "no new migrations needed" and "reuse the same distance utility" from F030/T088. Neither holds: T088 (`feed-place.ts`) resolves a *Place*, it computes no distance, and the F030 locality feed keys off **polygon containment** (`st_intersects`), not `ST_Distance`. There is no PostgREST-readable lat/lng on either `places.centroid` or `locations.geography`, and no existing distance helper. The distance-from-primary-home AC (`ST_Distance(places.centroid, locations.geography)`) can only run server-side in SQL, so T104 adds one minimal `security invoker` function, `venue_distance_meters(p_location_id)`.

**Why:** The function is the smallest correct way to satisfy the header's distance AC. `security invoker` means `member_place_interests` owner-RLS scopes it to the caller (an auth'd Member reads only their own `primary_home`); an anon caller matches no row → NULL → the header omits the line. `places`/`locations` are anon-readable, so no elevated rights. No table, column, RLS policy, or event type added.

**Disposition:** accepted-as-is. No SPEC-PATCHES entry — the ticket Note was a wrong premise about existing utilities, not a product-spec gap. Live-DB verification of the RPC is the downstream `test`/deploy-checklist step (no local Postgres in this build env; the function is parameterized + RLS-scoped by construction).

## Deviation 3 — Location resolves by globally-unique slug; there is no `locations.place_id`

**What:** The ticket AC says "Fetch the Location ... `locations` WHERE `place_id` = resolved Place AND `slug` = param." `locations` (migration 007) has **no `place_id` column** — `slug` carries a global `UNIQUE` constraint. Resolution keys off the slug alone (mirroring the Group dispatch, where `groups.slug` is likewise globally unique); the place path is breadcrumb/URL context only.

**Why:** The data model has no Location→Place FK at b1 (Locations carry `geography`, not a Place reference). Slug-uniqueness makes the lookup unambiguous. Matches the shipped `resolveShop` pattern.

**Disposition:** accepted-as-is. No SPEC-PATCHES entry — consistent with the existing Location schema and the Group dispatch precedent.

## Deviation 4 — Hero image always collapses (no image column on `locations` at b1)

**What:** The header AC renders a hero "if `locations` has an associated image." `locations` has no image column at b1. `resolveVenue` returns `heroImageUrl: null` unconditionally, so the hero space collapses entirely (the AC's no-image branch). The component's image path exists and is unit-tested for when an image source lands (T2 photo galleries).

**Why:** Faithful to the "no image → hero collapses, no empty container, no ARIA role" AC without inventing a schema column outside ticket scope.

**Disposition:** accepted-as-is.

## Deviation 5 — Owning-Group resolution + content sections deferred to T105

**What:** The ticket's Data-fetching AC lists "Resolve the owning Group (`anchor_location_id` … `ORDER BY created_at ASC LIMIT 1`)." Nothing in the T104 *shell* (header / CTAs / About) consumes the owning Group — it scopes the "What's happening here" / "What's happening nearby" sections, which the prompt and the ticket assign to T105. Resolving it in the shell would be dead code. The owning-Group query + the section frames (including the empty-state and minimal-page variants) move to T105 where the sections that consume them live.

**Why:** "Delete unused code" / no over-engineering. T104 stays exactly the shell the prompt scoped (route, header, CTAs, About, auth gating); T105 adds the sections + their owning-Group dependency together.

**Disposition:** accepted-as-is. Tracked by the T104→T105 dependency already noted in the ticket.

## Deviation 6 — Cross-ticket build-blocker fixed forward (T102's `'use server'` file)

**What:** `npm run build` failed before any T104 code ran: `src/app/_actions/saved-search-actions.ts` (T102, commit d85a54c) exported a **synchronous** helper (`buildVenueFollowLabel`) from a `'use server'` module, which Next 16 rejects ("Server Actions must be async functions"). It blocks the build on `main` too. Fixed forward by extracting the pure helper to `src/lib/saved-search/venue-follow-label.ts` and re-importing it in the action and its test (no behavior change; the T102 unit tests still pass).

**Why:** A pre-existing breakage on the critical path — T104 cannot produce a passing build without it. The fix is mechanical and preserves T102's tested behavior. Per "fix forward," documented rather than reverted.

**Disposition:** accepted-as-is. No SPEC-PATCHES entry — build-config conformance, not a spec gap.

## Note — private-venue gating via RLS (owner preview)

Private/soft-deleted Locations yield no row to non-owners → 404 (matches the scenario's "404 to non-owner viewers"). The Location *owner* can still read their own private venue (RLS `locations_owner_read`) and sees it as a preview — the same pattern as the Shop draft preview. This is the scenario's intent ("404 to non-owner"), slightly looser than the ticket's blanket "private → 404." Recorded as a decision; no code change.
