# T119 — Canonical Item URLs and browsable-kind withholding

## Deviation 1 — `wonder` is withheld despite `item.md` tiering it T1

**What:** `product/systems/item.md` § Item kinds tiers `wonder` as **T1** and states that a
Person can create an Item of kind product, service, gathering, *or* wonder. T119 withholds
`wonder` from every browse surface alongside the three T2 kinds.

**Why:** The tier is a statement about design intent, not about what resolves. `wonder` has its
child table (`item_wonders`, shipped in 015) but no composer, no detail page, and no response
affordance — at v1 it behaves exactly like the T2 three: a card that opens nothing. Shipping it
because the spec calls it T1 would put a link to a 404 on the feed to honour a tier label.

**Disposition:** flag-for-spec-revision — **Type A** (authoring drift, no architectural decision).
`item.md`'s tier claim is still the right target state; nothing about it needs re-deciding. When
`wonder` gets its composer and page, adding it to `BROWSABLE_KINDS` is a one-line edit and the
spec needs no change. Flagged for `tidy` only if `wonder` has not shipped by the b2 boundary,
at which point the T1 claim is stale rather than merely ahead of the build.

## Deviation 2 — The kind-filter pill row lost three shipped pills

**What:** T114 shipped seven Explore kind pills (All / Events / Products / Services / Ideas /
Offers / Asks). T119 derives the row from `BROWSABLE_KINDS`, leaving four (All / Events /
Products / Services). Three shipped controls are gone from the surface.

**Why:** Not in the ticket as written; found during build and predicted by `review-F054`
§ Sibling-consistency findings, which flagged that a facet for a kind the index can never return
is a dead control. Withholding the kinds without withdrawing their pills would have converted
three working filters into three that always render the empty state — which reads as a broken
filter rather than an unbuilt feature, and is a worse outcome than either option the decision
weighed.

**Disposition:** No spec revision needed. `KIND_FILTERS` is now derived rather than listed, so
the pills and the browsable set cannot drift apart again. This is the review's binding note 3
("one list, one edit to reverse") applied to a second consumer.

## Deviation 3 — A third 404 cause the decision stub did not name

**What:** `decision-item-canonical-urls.md` identified two causes (wrong link shape for
Group-filed rows; four kinds with no page). A third existed: attribution on the Group path read
`items.brand_label`, which is populated only from `group_businesses.display_name`, and every
resolver returned `null` when it was absent. A Group event filed under a non-business Group
therefore 404'd **at the resolver even with a correct URL**.

**Why:** The stub reasoned from `itemHref` outward and never reached the resolvers. The seeded
Repair Cafe — filed under an `event_anchored` Group — is the live instance, and Group events are
v1 scope, so every Group event would have hit it.

**Disposition:** flag-for-spec-revision — **Type A**. Fixed uniformly across all three resolvers
(`brand_label ?? groups.name`). Neither `groups.md` nor `item.md` says what a Group-filed Item is
credited to when the Group is not a business; both describe brand resolve-up for `kind='business'`
only. `review-F054` § Owed after build asks for one sentence in `groups.md`. Not blocking.

## Deviation 4 — Withholding is applied after the RPC limit on two read paths

**What:** The feed and the two venue sections read through RPCs that apply their own `limit`
before TypeScript filters withheld kinds, so a page can return fewer rows than requested. Explore
and the Member page filter server-side and are unaffected.

**Why:** Pushing the filter into `locality_feed_items`, `venue_nearby_items`, and
`venue_hosted_items` would mean changing three function signatures for a filter expected to be
removed kind by kind as each detail page lands. The ticket ruled MV and feed-RPC changes out of
scope.

**Disposition:** Accepted, and named rather than left implicit. At b1 volumes (16 seeded Items
against a limit of 50 for the feed and 20 for nearby) it cannot under-fill. The trigger to push
the filter down is a real page reaching its limit — worth re-checking when seeded or real content
passes roughly 20 Items in one locality.

## Deviation 5 — Migration applied by hand, not by the ticket

**What:** `037_group_url_prefixes.sql` was applied to the local database during build and must be
applied to production separately.

**Why:** This project has no migration runner yet — `playbooks/deployment-pipeline.md` records
that SQL is applied by hand in the Supabase dashboard, with the CLI adoption still a Phase 1 item.
The sandbox additionally blocked the direct production write.

**Disposition:** No drift from the ticket; recorded because the deploy is not complete when the
code merges. **The migration must land on production before the deploy, or every Group-filed link
falls back to the Member path and the 404s persist.** Both functions are `create or replace` plus
grants — additive, idempotent, and touching no data.
