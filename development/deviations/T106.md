# T106 — Add `starts_at` to the `discoverable_items` MV

## Deviation 1 — Past + dateless gatherings are HARD-FILTERED from all three RPCs, not sorted

**What:** The ticket (step 3) frames the locality change as a **sort** ("incorporate `starts_at` into its sort"). PM direction (2026-06-16, before commit) changed this to a **hard exclusion** applied uniformly across all three discovery RPCs: `locality_feed_items`, `venue_nearby_items`, and `venue_hosted_items` (the last recreated here, originally from migration 033). Each now carries two WHERE predicates:

```sql
and (<starts_at> is null or <starts_at> >= now())          -- past gatherings out; non-gatherings pass
and (<kind> <> 'gathering' or <starts_at> is not null)     -- dateless gatherings out
```

`locality_feed_items` drops the earlier bucket CASE entirely; its ORDER BY is now tag-boost → `starts_at asc nulls last` → `published_at desc`. (An intermediate revision used a 3-bucket sort to keep past events off the top; the PM preferred removing them outright.)

**Why:** A past or not-yet-scheduled gathering shouldn't surface on any discovery surface — sorting it to the bottom still showed it. Hard exclusion is the cleaner rule and is consistent across all three RPCs. Non-gathering items (products/services — naturally `starts_at` null) pass both predicates unchanged, so the common feed is unaffected except that stale/dateless gatherings disappear. Satisfies the original acceptance #4 (remaining upcoming gatherings still sort ahead of non-gatherings via `starts_at asc nulls last`) and strengthens #1.

**Disposition:** accepted-as-is (PM-directed). Goes beyond the written ticket (sort → filter) and extends the filter to `venue_hosted_items`, which the ticket marked out-of-scope ("can add the filter independently if needed") — the PM opted to add it now for cross-RPC consistency.

## Deviation 2 — Static-shape test, not a live-DB behavioral test

**What:** Acceptance #1–5 are runtime behaviors (past-event filtering, next-occurrence sort, CONCURRENT refresh). No local Postgres in this build env, so `tests/migrations-t106.test.ts` asserts the migration's DDL shape (MV rebuild, `starts_at` source + select, unique index preserved, all indexes + grants recreated, both RPC filter/sort clauses). Live-DB verification is the deploy-checklist step.

**Why:** Matches the T103/T075 no-Docker precedent. The acceptance behaviors follow directly from the asserted SQL.

**Disposition:** accepted-as-is.

## Note — MV rebuild reproduces the visibility gate verbatim

The dropped/recreated MV's `WHERE` (state=published, not deleted, group null-or-`listed`-and-not-dissolved) is identical to migration 016. The only additions are the `item_gatherings` lateral join, the `starts_at` select, and the partial `starts_at` index. No visibility change. Drop is plain (no CASCADE): classic string-body SQL functions create no relation dependency, so the dependent RPCs and the refresh trigger survive by name resolution and are rebuilt regardless.
