# T132 — Founder membership role branches by Group kind

## Deviation 1 — ticket's predicted fixture fixes were unnecessary

**What:** The ticket's acceptance criteria named `evals/fixtures/F034-gathering.ts:239` and
`evals/fixtures/F033-venue.ts:337` as fixtures needing `role: 'owner'` corrected to `'steward'`,
based on research done before build started. Both lines turned out to belong to
`ensureBusinessGroup` helpers (`kind: 'business'` throughout) — `'owner'` was already correct
there. `F033-venue.ts:381` (`ensureInterestGroup`, kind='interest') already seeded `'steward'`
correctly. `supabase/seeds/the-good-place.sql:383/386` also already encode the split correctly.

**Why:** The pre-build research surveyed the pattern (`role: 'owner'` appearing near a Group
insert) without confirming each hit's `kind`. The actual bug was isolated entirely to
`src/actions/group/create.ts` — every eval fixture and seed file already modeled the ratified
owner/steward split correctly, presumably because whoever wrote them worked from the spec
directly rather than from the code.

**Disposition:** accepted-as-is; no fixture changes made. No `Type` classification needed — this
is a scoping correction inside the same ticket, not a spec-vs-code divergence.

## Deviation 2 — ticket did not anticipate `group.update_draft`'s own owner-only gate

**What:** The ticket scoped the founder-role fix to `group/create.ts` only. Code review (M2)
surfaced that `group/update-draft.ts`'s authorization check (`role = 'owner'` literal, no kind
branch) would have locked every non-business founder out of editing their own draft Group the
moment they correctly received `role='steward'` — a regression this ticket would have shipped
silently. Fixed in the same pass: `update-draft.ts` now derives its required role via the same
`managingRoleForKind()` used at creation (renamed from `founderRoleForKind` to reflect the
dual use — the founder's assigned role and the role required to manage a draft are the same
question).

**Why:** The ticket's own research (correctly) traced `item.create`'s ownership check as a
consequence of the role fix, but missed that `update-draft.ts` carries an identical,
independently-written owner-only gate one file over. Caught by M2 code review before commit,
which is the point of running M2 before the permission prompt rather than after.

**Disposition:** accepted-as-is; fixed in the same commit as the rest of T132, not deferred.

## Deviation 3 — a second, unrelated bug's fix rides along: the acquisition prompt now correctly fires for non-business founders

**What:** `member.md` § Prompt-on-acquisition (Ratified 2026-06-03) already specifies the
discoverability prompt fires on "any membership in a kind='business' Group, **or a steward role
in any Group**." `acquisition-prompt.ts`'s qualifying query already encoded exactly this. Because
`group/create.ts` never actually produced a `'steward'` role for any Group, that half of an
already-ratified feature silently never fired. It now does, correctly, as a direct consequence
of this ticket's fix — not a new decision.

**Why:** Recorded because it's a real, user-visible behavior change (Members founding a run
club or a family Group will now see a one-time discoverability prompt they never saw before) and
the stale comment in `create.ts` claiming this path was a no-op needed correcting regardless.

**Disposition:** accepted-as-is; this is the spec's own intent finally reachable, not scope creep.
