# Agent-Assistance Security & Privacy Review — 2026-05-09

**Reviewer:** Independent (security/privacy focus)
**Artifacts:** `delegation.md`, `member-self-record.md`, `skills.md`, `member-operations.md`, ADRs 6/7/8/9, `policy.md`, `principles.md`.

## Verdict

**Specific structural enforcements required before b1 ships.** The policy posture and three-filter discipline are honest and the b1 substrate (audit columns, scope enum, export/purge) is the right shape. But the docs lean heavily on prose for commitments that can and must be enforced in schema, RLS, separate Postgres roles, or transaction-bound triggers. As drafted, ~60% of the load-bearing commitments are policy-only, including some — Self-Record cross-Member invisibility, recurring-payment caps, k-anonymity floor, atomic delete cascades, separation between recommendation services and Self-Record storage — where future engineering discipline alone is not a sufficient guarantee. Six abuse vectors are not yet addressed at the spec level; four lifecycle gaps will produce orphans; two audit gaps mean a Member cannot fully see what was done on their behalf. None of these are architecture-breakers, but they are spec-level work that belongs in the docs before tickets are written, not after.

## Structural vs. policy enforcement

| Commitment (source) | Current enforcement | Recommended enforcement |
|---|---|---|
| Self-Record never visible to other Members (`member-self-record.md` Defaults) | Policy-only (no surface reads it at b1) | **RLS** on `member_self_records` + `member_self_record_entries`: `SELECT` restricted to `member_id = auth.uid()`. Separate Postgres role for the recommendation/feed services with `REVOKE SELECT` on both tables. Migration test asserts the recommender role's grants. |
| Self-Record never used as training data (`member-self-record.md` Defaults; ADR-6) | Policy-only | **Separate Postgres role** for any training/export pipeline with no grant on Self-Record tables. Periodic CI assertion that no service code outside `actions/self_record/*` imports the model for these tables. |
| Self-Record purge atomic with account deletion (`delegation.md`, `member-self-record.md`) | Policy-only ("purged in the same transaction") | **`ON DELETE CASCADE`** FK from `member_self_records.member_id` and `member_self_record_entries.member_id`. Explicit transaction-bound `member.delete` action that runs all cascades inside a single SERIALIZABLE transaction with a post-commit verification query. |
| Delegation revoked on member delete (`delegation.md` "Rules out") | Policy-only | **`ON DELETE CASCADE`** on `delegations.granting_member_id`; trigger that emits `delegation.revoked` events for each affected row (so audit log captures the cascade). |
| `recurring_payment` caps required, no nullable (`delegation.md` Policy posture) | Policy-only at b1; ADR-9 says "schema-enforced at b2" | Explicit at b1: a separate `delegation_recurring_payment_caps` child table joined 1:1 to `delegations` rows whose scopes include `recurring_payment`, with **`CHECK (max_per_transaction_cents > 0 AND max_per_month_cents > 0 AND array_length(recipient_allowlist, 1) >= 1) NOT NULL`**. Insert trigger refuses Delegations with `recurring_payment` in scopes if no caps row. Don't defer this to b2 — the schema must reject malformed rows before the surface ships. |
| Confirmation-required scopes cannot be exercised without per-action human confirmation (`delegation.md` T2; ADR-6) | Policy-only ("schema-level constraint" in ADR-6 but no schema given) | **Action-handler gate** (per ADR-7): handlers for `*_publish` actions assert a `confirmation_token` parameter and validate it server-side against a short-lived `pending_confirmations` table keyed on `(member_id, action, payload_hash)`. Without it, the handler hard-rejects regardless of caller (composer, assistant, MCP). Token issued only by an interactive UI surface; assistants cannot mint one. |
| Skill execution model: scopes used must equal scopes requested (`skills.md` Open questions) | Policy-only ("track scope-use vs scope-declared") | **Trigger on `delegation.scope_used`** that increments per-(skill, scope) counters in a `skill_scope_usage` table. **`/you/skills`** surfaces unused scopes after a configurable threshold (e.g., 30 days subscribed, scope never used). Allow per-scope revocation without unsubscribe (Member-driven scope reduction). Spec this in `skills.md` T2, not as an open question. |
| K-anonymity floor N≥10 for aggregate analysis (`member-self-record.md` Policy posture) | Policy-only | **Action-layer constraint** in the aggregate-analysis handler: a SQL function `assert_k_anon(bucket_count int, k int default 10)` called inside every aggregate query that raises if `bucket_count < k`. Aggregate queries cannot be issued ad-hoc; they must go through a named, reviewed handler. Spec the function and the rule in `member-self-record.md`. |
| Self-Record entries without `confirmed_at` are proposals, not record (`member-self-record.md` T2) | Trigger/code-enforced (claim) but no spec | **CHECK constraint** on the denormalized spine: trigger that maintains current section values reads `WHERE confirmed_at IS NOT NULL`. Add a `BEFORE INSERT` trigger on the spine table that refuses any non-trigger-driven write (i.e., the spine is only updated by the materialization trigger, never directly). |
| Skill subscription revoke ↔ Delegation revoke atomicity (`skills.md`) | Policy-only ("revokes the Delegation atomically") | **Single transaction-bound action** `skill.unsubscribe` that updates both rows. **DB-level guarantee**: a deferrable constraint or a trigger that asserts every active `skill_subscriptions` row has a matching active `delegations` row (and vice versa for `grantee_kind = 'skill'`). |
| `staff` Operation requires operator confirmation before grants (`member-operations.md` T2) | Policy-only at b1; described for T2 | **CHECK / trigger** that any `staff_edit_items` Delegation issuance requires the corresponding `member_operations` row to have `confirmed_by_operator_at IS NOT NULL`. Reject otherwise. Spec the constraint in `delegation.md` alongside the scope itself. |
| Per-Skill Self-Record section scoping (T3) | Policy-only — design deferred | When this lands, a `skill_self_record_grants` join table with explicit `(skill_subscription_id, section)` rows; no row, no read. Don't plan to enforce via "the assistant respects the manifest" — assistants are untrusted. |
| Cross-Member sharing time-bound + revocable (`member-self-record.md` Policy posture) | Policy-only | **`expires_at NOT NULL`** on the share table; **RLS** policy on `member_self_records` extended to `OR EXISTS (SELECT 1 FROM self_record_shares WHERE ... Existing subscriptions stay pinned to old version until Member taps. Spec the comparison rule explicitly. |

## Abuse vectors not adequately mitigated

1. **Slow-burn scope hoarding by malicious Skill authors.** The "scope-use vs scope-declared" mitigation (`skills.md` Open questions) detects scopes never used. A sophisticated attacker exercises every requested scope once a quarter to keep the counter non-zero, then quietly uses the over-broad scope for the actual abuse. *Spec-level mitigation needed:* per-scope "median use rate" over a rolling window, not "ever used." Also: declared scopes that exceed the published norm for the Skill's loop family should require platform review at publish, not at subscribe.

2. **Coercive cross-Member sharing.** `member-self-record.md` opts in cross-Member sharing as "useful for handing operating notes to a new staff Member." The same affordance lets an operator condition employment on sharing voice/tastes/refusals ("share or you can't work my booth"). *Spec-level mitigation needed:* sections beyond `pinned_facts` (i.e., `voice`, `tastes`, `refusals`, `current_focus`) refuse cross-Member sharing in any scope, period. If the sharing use case is operating notes, the section to share is `pinned_facts`; the others have no operational reason to leave the Member. Today the spec says "per-section grain" without naming which sections are shareable at all.

3. **Operator-initiated false `staff` claims (inverse of the documented vector).** The doc mitigates *Member-initiated* false `staff` claims via operator confirmation. The inverse — an operator declaring a `staff` Operation *for* another Member they do not employ, e.g., to attach a problematic Member to their own booth in the audit trail and damage their reputation — is not addressed. *Spec-level mitigation needed:* `staff` Operations can only be declared by the Member-as-staff, not the operator. Operator's role is confirmation only. The schema should enforce this: the `member_id` on a `capacity='staff'` row must equal `auth.uid()` at insert time.

4. **Recurring-payment Delegation: scope creep across versions.** ADR-9 commits to a published cap and 90-day re-opt-in for changes to the *Skill payment cut*. Equivalent protection for the `recurring_payment` Delegation's caps and allowlist is not specified. A Skill author could publish a new version that requires a higher `max_per_transaction_cents` ceiling and rely on subscriber inertia. *Spec-level mitigation needed:* any change to a Delegation's cap fields requires a fresh grant flow, not an in-place update. The `delegations` row is immutable on cap fields; cap changes mint a new row.

5. **Re-identification via aggregate analysis at low Member counts.** K-anonymity N≥10 protects against direct re-identification but not against quasi-identifier reconstruction (zip + Operation capacity + market-day pattern). *Spec-level mitigation needed:* (a) the aggregate handler must reject queries whose grouping keys collectively produce buckets near the floor, not just queries below the floor; (b) suppress all results for a bucket if any cell drops below floor (cell suppression, not just bucket suppression); (c) `member-self-record.md` should commit to differential-privacy noise on numeric counts at b3 or earlier — N≥10 alone is insufficient for the bakery example.

6. **Delegation token theft / federation handoff token reuse.** Spec is silent on token rotation, IP/device pin, refresh, or replay. The federation handoff (`delegation.md` T3) compounds this: a federation peer's compromised token can read everything the Member granted them, indefinitely until the Member notices. *Spec-level mitigation needed:* every Delegation issuance produces a token whose claim includes a short-lived (≤24h) authentication window plus a long-lived authorization window; revocation is published to a fast-path cache that the action handler checks on every call (not just a database read). Federation tokens additionally require a peer-side proof-of-possession (DPoP or equivalent) so that token theft alone does not enable use.

## Data lifecycle gaps

1. **Account deletion fan-out is not specified.** ADR-6 and the specs say purges are atomic but never enumerate the cascade set: `member_self_records`, `member_self_record_entries`, `delegations`, `skill_subscriptions`, `member_operations`, plus the `staff` Operations *other Members hold against this Member* (which become orphaned `operating_for_member_id` references), plus `item_collaborators` rows, plus the cross-Member share table. *Recommended:* `delegation.md` (or a forthcoming `member.md`) carries an explicit "On Member delete" matrix listing every table touched, every action taken, and whether the artifact is deleted, anonymized, or retained.

2. **Skill removal mid-task.** `skills.md` says removal "revokes Delegations atomically with notification" but does not address: drafts the Skill produced that the Member has not yet reviewed; Self-Record entries proposed under that Skill still in `proposed` state; the `skill_subscriptions.delegation_id` FK after Delegation deletion. *Recommended:* (a) drafts persist independently of the Skill; (b) pending proposals are auto-rejected with `rejected_reason = 'skill_removed'`; (c) Delegations are *revoked* (set `revoked_at`), not deleted, so the FK survives.

3. **Operation ending leaves dangling links.** A `sole_personal` Operation is ended → Items carrying that brand_label still exist. Staff who had `operating_for_member_id` pointing at the operator's now-ended Operation surface as orphans. *Recommended:* `member-operations.md` carries explicit semantics for Item brand_label after Operation end (working answer: persist the label, render with "previously operated as" annotation), and for staff Operations whose operator ended their linked Operation (auto-end the staff Operation with `revoke_reason = 'operator_ended_operation'`).

4. **Delegation expiry without grace.** `delegations.expires_at` is enforced server-side; expired calls are rejected. There is no spec for what happens to in-flight async work (a recurring-payment execution mid-processor-call, a Skill scheduled-job that fired before expiry but completes after). *Recommended:* `delegation.recurring_payment_executed` events are append-only and complete even after expiry if the action started before; no new actions begin after `expires_at`. Spec the boundary explicitly.

5. **Federation handoff: what stays, what goes.** ADR-6 commits to "identity, Self-Record, and (where flagged) Delegations follow the Member." It does not say what happens to non-portable artifacts: Items the Member created, Operations against this platform's Communities, audit history, response artifacts other Members made on the Member's Items. *Recommended:* `member-self-record.md` T3 names the federation-handoff cleanup contract — what's exported, what's tombstoned, what's retained for other Members' integrity (their RSVPs to the Member's gathering shouldn't disappear).

6. **Inferred-update evidence retention.** `member-self-record.md` carries `evidence_event_ids` for inferred entries but says nothing about what happens when those event-log entries themselves age out (event log is partitioned monthly per `item.md`). *Recommended:* either pin evidence events from aging, or accept that old inferred entries lose their evidence link and surface that in the diff view at T3 ("evidence no longer retrievable"). Don't leave it implicit.

## Auditability gaps

1. **Member cannot see scope-by-scope what each Skill actually read.** `delegation.scope_used` events fire per action but the spec doesn't promise a Member-facing view of "this Skill read your `pinned_facts` 47 times this month." Without that, per-Skill scope reduction at T3 is theoretical. *Recommended:* `/you/skills/[id]/access-log` ships at the same time as the subscription surface (T2), reading directly from `delegation.scope_used`, partitioned per Skill.

2. **No event for "the assistant proposed an inferred Self-Record update and dropped it."** The spec logs `self_record.entry_proposed`, `_confirmed`, `_rejected`. It does not log a *suggestion the assistant generated and decided not to surface* (e.g., because of the cooldown). A Member auditing "what does the assistant think it knows about me" cannot see suppressed inferences. *Recommended:* add `self_record.inference_suppressed` event, fired when the assistant computes an inference but does not surface it (with reason: cooldown, low confidence, conflict).

3. **No event for cross-Member share read.** `self_record.shared_with` (or equivalent) is missing from the event log enumeration. A Member who shared `pinned_facts` with a colleague cannot see *when the colleague's assistant actually read it.* *Recommended:* every read of a shared Self-Record section by a non-owner emits `self_record.shared_section_read` with reader Member id and timestamp, surfaced in the sharer's audit log.

4. **Skill version diff is described in UX but not in the event log.** `skill.version_published` fires, but the diff (especially scope additions) is not preserved as a structured event payload — the spec references "a notification with a diff of changes" without committing to durable storage. *Recommended:* `skill.version_published` payload includes `added_scopes`, `removed_scopes`, `manifest_diff_url` so the audit trail is complete after the notification UI is replaced or redesigned.

## Two questions that would change my verdict

1. **Will the action layer be enforced as the only write surface via Postgres role separation, or as a code convention?** ADR-7 commits to "every write is a documented action" but does not say whether the application's database role can write directly to e.g. `member_self_records` or only through `SECURITY DEFINER` functions wrapping the actions. If the former, every privacy commitment that says "we never write X without Y" is one rogue migration or one bypassed code review away from violation. If the latter, the structural enforcement is real. The answer determines whether ~30% of the policy-only commitments above can be downgraded to "structurally enforced via the action-layer role."

2. **What is the platform's posture when its chosen LLM provider's TOS changes mid-Member-relationship?** Self-Record content reaches the inference-time provider on every assistant session. ADR-9 commits to re-confirmation when the *platform* changes opt-ins. There is no commitment about provider-side changes (provider starts retaining inputs for safety review; provider is acquired; provider's privacy policy changes). The Member opted in to "Anthropic at terms X"; the platform now ships them under terms Y. If the platform takes the position "your provider relationship is your problem," the Self-Record commitments are softer than they appear. If the platform takes the position "we mediate the provider relationship and re-prompt you on material changes," the commitments hold. The answer changes whether the headline "the Self-Record is the Member's instrument, not the platform's" survives provider churn.
